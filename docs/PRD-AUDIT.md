# MyMob iOS PRD audit — 31 October 2026

Baseline: `../../PRD.md` (30 October 2026), app commit
`553b3691d6883bf6164468a700c7e1717b7b7dd8` and server commit
`2cb391b447f454f29f5226a0031f6ad28d438786`.

The app implements most P0 screens, but several privacy and offline guarantees
are incomplete. This report records missing behavior; it does not fix it.
Paths below are relative to `DatathonApp/DatathonApp/` unless otherwise noted.
See the [server and cross-platform audit](../../server/docs/PRD-AUDIT.md) for
API defects, clinic editing, insights and deployment verification.

## P0 gaps

### 1. Carer revocation does not purge cached appointments

`Sync/SyncEngine.swift:155–185` only upserts appointment deltas.
`Networking/APIModels.swift:303,341` has no appointment-removal contract.
`Features/Health/AppointmentsView.swift:27–28` reads all cached appointments.
Receiving a revoked carer relationship does not remove health records; lite
sync does not receive the relationship either. Thus previously cached patient
details remain accessible even after the carer reconnects successfully.

**Close when:** after revocation, both full and lite sync remove the patient's
appointments and detail data. Include access gained after the current cursor,
not just access lost. Instant revocation while disconnected is not possible;
the defect is stale authorization after reconnecting.

### 2. Shared-device notification handling lacks recipient routing

`App/AppEnvironment.swift:118–128` registers the active user, displays incoming
notifications, and opens the current Calendar on every tap. It does not check
which profile owns the notification. The server retains all user/device
registrations and sends to each recipient's registered tokens.

**Close when:** switching from A to B prevents A's reminder being treated as
B's; notification navigation identifies the correct person and respects their
PIN. Generic previews are already implemented.

### 3. A dropped direct-post response can create duplicate posts

`Features/Groups/GroupFeedView.swift:310,322` sends a direct request with a new
mutation ID. The fallback at `:336` queues it with another ID generated by
`Persistence/CacheModels.swift:52`. If the server committed before the response
was lost, it sees the retry as a new post. A related direct comment-reaction
fallback at `Features/Posts/CommentsSection.swift:243–258` can double-toggle
an already-applied reaction.

**Close when:** one stable mutation ID survives direct request, timeout and
queued retry; reaction retries specify the intended state. Test a response
drop after server commit and assert one post / the intended reaction.

### 4. Youth onboarding and guardian consent are unfinished

`Features/Auth/SignInFlowView.swift:74` collects phone and name, not date of
birth or guardian. `Features/Groups/GroupsView.swift:190` sends only the join
code/group ID. `Features/Groups/ModerationView.swift:65` displays consent status,
but no app call submits guardian consent. The backend endpoint exists, and its
age check is bypassed for unknown ages, so seeded youth records are not an
end-to-end onboarding solution.

**Close when:** a newly registered minor can link a guardian and obtain consent
before Elder approval, with no unknown-age bypass of the intended policy.

### 5. Satellite queue batching and priority do not match the PRD

`Sync/SyncEngine.swift:94–109` can make up to three requests per flush and sends
the complete FIFO queue rather than prioritizing confirmations and RSVPs. It
has no 200-write cap despite the server rejecting larger batches. An oversized
offline queue therefore cannot drain. Ordinary posts and reactions are also
sent without the required priority/defer policy.

**Close when:** a foreground satellite sync uses one bounded batch, prioritizes
appointment confirmations/RSVPs and retains deferred writes for later syncs.
Test a queue over 200 items, an interrupted request and recovery on normal
coverage. Preserve text comments as required by the PRD.

### 6. Server invalidation and pagination need matching client support

The server omits rejection tombstones for readers other than the author and
advances cursors past capped results. Removed membership content is not purged
either. A healthy queue alone does not make the offline cache authoritative.

**Close when:** previously published content disappears after moderation or
membership removal, and more changes than a response cap can be drained
without losing rows. See server audit findings 3 and 4.

## Implemented from source

- Phone OTP, four-digit PIN, Keychain storage, profile-separated caches/queues,
  profile switching and background locking.
- Group search/join, Elder membership/post/provider decisions, pinning,
  community feed, events and queued RSVP.
- Patient invite acceptance, appointment details, attendance confirmation,
  carer nomination and explicit revocation requests.
- Cached feed/events/appointments/comments; dedicated lite URLSession,
  constrained-path detection, satellite toggle/banner and separate sync cursors.
- One-level comment threads, reporting, reactions, moderation and thread locks.
- Cultural controls during composition, normal deceased-warning gates,
  text-only sorry-business posts and language catalogs/community translations.

## Verification and demo readiness

This was a source audit. No iOS build, simulator/device test, actual notification
delivery or Network Link Conditioner run was performed. Xcode 27.1 is installed,
but availability is not a passing build. Existing sync tests cover retries,
profile queue separation, server-wins updates, RSVP coalescing, post removals
and basic lite sync; they do not establish the missing cases above.

Server checks passed: 28 unit tests, TypeScript and ESLint. Read-only database
queries confirmed populated views for all four insight families. Those checks
do not prove the iOS journeys. Rehearse both complete demo flows, including
second-device carer access, airplane-mode confirmation, real SMS or clearly
labelled outbox fallback, and measured lite payloads; time two runs and record
a backup before claiming judging readiness.
